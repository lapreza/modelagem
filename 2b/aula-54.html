Semana 14 — Aula 2

Modelagem de Dados com UML

O Diagrama de Classes na Engenharia de Dados

Embora o Modelo Entidade-Relacionamento (MER) seja a notação clássica para bancos relacionais, o Diagrama de Classes da UML (Unified Modeling Language) é amplamente utilizado no desenvolvimento orientado a objetos para representar tanto a estrutura lógica da aplicação quanto o mapeamento objeto-relacional (ORM) do banco de dados.

1. Correspondência entre UML e Modelo Relacional

Para converter um Diagrama de Classes persistente em um esquema físico SQL (DDL), aplicamos regras diretas de mapeamento estrutural: 

+---------------------------+----------------------------------------+
| Elemento UML              | Equivalente no Banco Relacional        |
+---------------------------+----------------------------------------+
| Classe Persistente        | Tabela (CREATE TABLE)                  |
| Atributo da Classe        | Coluna / Campo da Tabela               |
| Objeto (Instância)        | Registro / Linha (Tupla)               |
| Associação 1:N            | Chave Estrangeira (FK) no lado N       |
| Associação N:M            | Tabela Associativa (Intermediária)     |
| Composição (Losango Cheio)| FK com ON DELETE CASCADE               |
+---------------------------+----------------------------------------+

2. Multiplicidades e Implementação SQL

Na UML, a cardinalidade é chamada de Multiplicidade e indica quantas instâncias de uma classe podem estar vinculadas a uma instância de outra classe:

  • 1 ou 1..1: Exatamente um (ex: Um Aluno possui exatamente um Prontuário).
  • 0..1: Zero ou um (opcional / anulável na Foreign Key).
  • 1..* ou *: Um ou muitos / Zero ou muitos (lado N recebe a Chave Estrangeira).
-- Exemplo de Associação N:M (Aluno * --- * Disciplina) convertida em SQL
CREATE TABLE alunos (
    id_aluno INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL
);

CREATE TABLE disciplinas (
    id_disciplina INT PRIMARY KEY,
    titulo VARCHAR(100) NOT NULL
);

-- Classe Associativa UML convertida em Tabela Intermediária
CREATE TABLE aluno_disciplina (
    id_aluno INT REFERENCES alunos(id_aluno),
    id_disciplina INT REFERENCES disciplinas(id_disciplina),
    semestre VARCHAR(10) NOT NULL,
    PRIMARY KEY (id_aluno, id_disciplina, semestre)
);

3. Mapeamento de Herança (Generalização / Especialização)

Bancos de dados relacionais tradicionais não suportam herança nativa entre tabelas. Existem três estratégias padrão para mapear hierarquias de classes UML (ex: Pessoa como superclasse de Aluno e Professor):

1. Tabela Única (Single Table Inheritance): Todas as subclasses são armazenadas em uma única tabela grande com uma coluna discriminadora (ex: tipo_pessoa).

2. Tabela por Classe (Class Table Inheritance): Cria-se uma tabela para a superclasse e uma tabela separada para cada subclasse ligadas por chave primária compartilhada (1:1).

3. Tabela por Classe Concreta (Concrete Table Inheritance): Cria-se apenas as tabelas das subclasses, repetindo os atributos herdados da superclasse em cada uma.

Atividade de Fixação

  1. Como uma associação de multiplicidade muitos-para-muitos (*..*) entre duas classes UML é implementada fisicamente em um banco de dados relacional?
  2. Qual é a diferença semântica entre Agregação (losango vazio) e Composição (losango preenchido) na UML e como a Composição é refletida na criação da Foreign Key em SQL?
  3. Compare as estratégias de mapeamento de herança Single Table e Class Table apontando uma vantagem e uma desvantagem de cada abordagem.

Aula 62: Índices em Bancos de Dados Relacionais

Entenda como os índices aceleram drasticamente as consultas (SELECT) usando estruturas como B-Tree e Hash, quando criar índices simples ou compostos e quais são seus custos nas operações de escrita.

1. O que são Índices e Como Funcionam?

Um Índice (Index) é uma estrutura de dados auxiliar mantida pelo SGBD que aponta diretamente para a localização física dos registros em uma tabela — de forma análoga ao índice remissivo no final de um livro técnico.

Sem um índice na coluna filtrada, o SGBD precisa realizar uma varredura completa linha por linha, conhecida como Full Table Scan. Em uma tabela com 5 milhões de registros, isso pode levar vários segundos; com um índice adequado, a mesma busca ocorre em milissegundos.

Nota Importante: Quando você define uma PRIMARY KEY ou uma restrição UNIQUE em uma tabela, o SGBD cria automaticamente um índice para aquela coluna. Já colunas de FOREIGN KEY ou colunas usadas frequentemente em filtros WHERE devem ser indexadas conforme a necessidade de desempenho.

2. Tipos Comuns de Índices

Tipo / Estrutura Funcionamento Melhor Caso de Uso
B-Tree (Árvore-B) Mantém os valores ordenados em uma árvore balanceada (padrão na maioria dos SGBDs). Comparações de igualdade (=), faixas de valores (>, <, BETWEEN), ordenação (ORDER BY) e prefixos (LIKE 'Ana%').
Hash Index Calcula um código hash direto para o endereço do registro em tempo constante $O(1)$. Apenas comparações exatas de igualdade (=). Não serve para intervalos (>, <) nem ordenação.
Índice Único (UNIQUE) Acelera buscas e garante que não existam valores duplicados na coluna indexada. Colunas como email, cpf ou codigo_rastreio.
Índice Composto Índice criado sobre duas ou mais colunas simultaneamente na mesma definição. Consultas que filtram juntas colunas específicas (ex.: WHERE estado = 'SP' AND cidade = 'Sumaré').

3. Criando, Removendo e Testando Índices em SQL

-- Criando um índice simples na coluna 'email' da tabela clientes
CREATE INDEX idx_clientes_email ON clientes(email);

-- Criando um índice único na coluna 'cpf'
CREATE UNIQUE INDEX idx_clientes_cpf ON clientes(cpf);

-- Criando um índice composto (a ordem das colunas importa!)
CREATE INDEX idx_vendas_data_status ON vendas(data_venda, status);

-- Verificando o plano de execução de uma consulta
EXPLAIN SELECT * FROM clientes WHERE email = 'rafael@exemplo.com';

-- Removendo um índice que não é mais utilizado
DROP INDEX idx_clientes_email ON clientes;

A Regra do Prefixo à Esquerda (Leftmost Prefix)

Em um índice composto (coluna_A, coluna_B), o SGBD consegue aproveitar o índice se a consulta filtrar por coluna_A sozinha ou por coluna_A AND coluna_B. Porém, se a consulta filtrar apenas por coluna_B, o índice composto geralmente não será utilizado.

4. O Custo dos Índices: Quando NÃO Criar?

Se índices deixam as consultas tão rápidas, por que não criar um índice em cada coluna de todas as tabelas?

  • Lentidão na Escrita (INSERT, UPDATE, DELETE): Toda vez que um registro é inserido, alterado ou removido, o SGBD precisa atualizar não apenas a tabela, mas também reequilibrar todos os índices associados a ela.
  • Consumo de Espaço em Disco e Memória RAM: Índices ocupam espaço físico adicional e disputam memória cache (Buffer Pool) com os dados reais.
  • Baixa Seletividade: Criar índice em colunas com pouquíssimos valores distintos (ex.: coluna booleana ativo com 0 ou 1) raramente traz ganho de performance, pois o SGBD lê quase metade da tabela de qualquer forma.
Atenção com Funções no WHERE: Aplicar funções diretamente sobre a coluna indexada — como WHERE YEAR(data_venda) = 2026 ou WHERE UPPER(nome) = 'JOÃO' — costuma invalidar o uso do índice B-Tree padrão, forçando um Full Table Scan.

5. Exercícios de Fixação

Analise as situações abaixo sobre indexação relacional:

1. Uma tabela logs_acesso recebe 50.000 inserções por minuto e quase nunca sofre consultas filtradas. O que acontece se criarmos 8 índices diferentes nela?

Ver resposta comentada
O desempenho de escrita (INSERT) cairá drasticamente e o consumo de disco disparará, pois o SGBD terá que atualizar 8 estruturas de índice diferentes para cada uma das 50.000 linhas gravadas por minuto, sem nenhum benefício real de leitura.

2. Qual estrutura de índice é mais adequada para otimizar a consulta SELECT * FROM pedidos WHERE data_pedido BETWEEN '2026-01-01' AND '2026-06-30'; — B-Tree ou Hash?

Ver resposta comentada
B-Tree (Árvore-B), pois ela mantém as chaves ordenadas e suporta buscas por intervalos/faixas (BETWEEN, >, <). Índices Hash suportam apenas comparações exatas de igualdade (=).

3. Qual comando SQL utilizamos antes de um SELECT para inspecionar se o SGBD está realmente utilizando um índice ou fazendo um Full Table Scan?

Ver resposta comentada
O comando EXPLAIN (ex.: EXPLAIN SELECT ...), que exibe o plano de execução escolhido pelo otimizador de consultas do SGBD.

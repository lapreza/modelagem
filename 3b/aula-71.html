Aula 71: SELECT com UNION e UNION ALL

Aprenda a combinar verticalmente os resultados de duas ou mais consultas SELECT utilizando operadores de conjuntos (UNION, UNION ALL, INTERSECT e EXCEPT), respeitando as regras de compatibilidade de colunas e otimizando desempenho.

1. Empilhando Resultados com UNION e UNION ALL

Enquanto o JOIN (Aula 67) combina tabelas horizontalmente (adicionando colunas lado a lado), os operadores UNION e UNION ALL combinam resultados verticalmente — empilhando as linhas retornadas por dois ou mais comandos SELECT em uma única lista resultante.

Regras Obrigatórias de Compatibilidade

  1. Mesma quantidade de colunas: Todos os SELECT participantes devem projetar exatamente o mesmo número de colunas.
  2. Tipos de dados compatíveis: Cada coluna correspondente na mesma posição deve ter tipo compatível (ex.: texto com texto, número com número, data com data).
  3. Nomes das colunas e Ordenação: Os cabeçalhos das colunas finais vêm sempre do primeiro SELECT, e uma cláusula ORDER BY final deve aparecer apenas no encerramento da última consulta.
Operador Tratamento de Duplicatas Desempenho no SGBD
UNION Remove linhas idênticas entre os conjuntos (aplica um DISTINCT implícito). Mais lento, pois precisa ordenar ou criar tabela hash para eliminar repetições.
UNION ALL Mantém todas as linhas de ambas as consultas, inclusive duplicadas. Muito mais rápido, pois apenas concatena os resultados sem custo de deduplicação.

2. Exemplos Práticos em SQL

-- Exemplo 1: Lista única de e-mails para campanha (UNION remove e-mails repetidos)
SELECT nome, email FROM clientes
UNION
SELECT nome, email FROM fornecedores
ORDER BY nome ASC;

-- Exemplo 2: Consolidando vendas atuais e histórico arquivado (UNION ALL é ideal!)
SELECT 
    id_pedido,
    data_pedido,
    valor_total,
    'ATUAL' AS origem_base
FROM pedidos_2026

UNION ALL

SELECT 
    id_pedido,
    data_pedido,
    valor_total,
    'HISTORICO' AS origem_base
FROM pedidos_arquivo_2025
ORDER BY data_pedido DESC;
Boas Práticas de Performance: Sempre que você souber previamente que os dois conjuntos não têm registros sobrepostos (como tabelas separadas por ano ou com uma coluna identificadora distinta como 'ATUAL' vs. 'HISTORICO'), utilize UNION ALL para evitar ordenações desnecessárias no servidor.

3. Outros Operadores de Conjunto: INTERSECT e EXCEPT

Além da união, o padrão SQL oferece outros dois operadores de teoria dos conjuntos que seguem as mesmas regras de compatibilidade de colunas:

  • INTERSECT: Retorna apenas as linhas que existem simultaneamente em ambos os SELECT (interseção).
  • EXCEPT (ou MINUS no Oracle): Retorna as linhas que existem no primeiro SELECT, mas não aparecem no segundo (diferença entre conjuntos).
-- Clientes que compraram em 2025, mas NÃO compraram em 2026
SELECT id_cliente FROM pedidos_2025
EXCEPT
SELECT id_cliente FROM pedidos_2026;
Portabilidade entre SGBDs: PostgreSQL, SQL Server, SQLite e MySQL (a partir da versão 8.0.31) suportam INTERSECT e EXCEPT. Em versões antigas do MySQL, esses dois operadores eram simulados via INNER JOIN e LEFT JOIN ... WHERE ... IS NULL.

4. Exercícios de Fixação

Verifique seus conhecimentos sobre operadores de conjuntos em SQL:

1. A consulta SELECT nome, cidade FROM clientes UNION SELECT nome FROM fornecedores; funciona corretamente?

Ver resposta comentada
Não, gera erro de sintaxe. O primeiro SELECT projeta 2 colunas (nome, cidade), enquanto o segundo projeta apenas 1 coluna (nome). Ambas as consultas devem possuir exatamente a mesma quantidade de colunas (ex.: preencher com NULL AS cidade na segunda).

2. Se a tabela A possui 500 linhas e a tabela B possui 300 linhas, qual será a quantidade exata de linhas retornadas por SELECT * FROM A UNION ALL SELECT * FROM B;?

Ver resposta comentada
Exatamente 800 linhas ($500 + 300$), independentemente de haver registros repetidos entre A e B, pois o UNION ALL não remove duplicatas.

3. Em uma consulta com UNION entre alunos(nome_aluno) e professores(nome_docente), qual será o nome da coluna exibida no resultado final?

Ver resposta comentada
Será nome_aluno (ou o apelido definido na primeira consulta), pois os metadados das colunas resultantes são sempre herdados do primeiro bloco SELECT.

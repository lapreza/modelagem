Aula 77: Backup e Recuperação de Dados

Compreenda os pilares da continuidade de negócios em SGBDs: métricas RPO e RTO, tipos de backup (Completo, Diferencial, Incremental e Log de Transações), backup lógico vs. físico, recuperação pontual (PITR) e a regra 3-2-1.

1. Métricas de Continuidade (RPO e RTO) e Tipos de Backup

Antes de escolher uma estratégia de cópia de segurança, todo administrador de banco de dados (DBA) define dois indicadores junto ao negócio:

  • RPO (Recovery Point Objective — Objetivo de Ponto de Recuperação): Quanto tempo de dados a empresa tolera perder em caso de desastre (ex.: um RPO de 15 minutos significa que o backup ou arquivamento de logs deve ocorrer a cada 15 minutos).
  • RTO (Recovery Time Objective — Objetivo de Tempo de Recuperação): Quanto tempo máximo o sistema pode ficar fora do ar até que o banco seja restaurado e volte a operar.
Tipo de Backup O que é Copiado? Velocidade do Backup Processo de Restauração
Completo (Full) Todos os dados e objetos do banco inteiro. Mais lento e ocupa mais espaço. Rápida: basta restaurar o último arquivo Full.
Diferencial Todas as alterações feitas desde o último backup Full. Intermediário (cresce até o próximo Full). Moderada: restaura o último Full + o último Diferencial.
Incremental Apenas as alterações feitas desde o último backup (seja Full ou Incremental). Muito rápido e ocupa pouco espaço. Mais lenta: exige o Full + toda a cadeia sequencial de Incrementais.
Log de Transações (WAL / Binlog) Registro contínuo de todas as operações gravadas no log do SGBD. Contínuo (em tempo real ou poucos minutos). Permite PITR (Point-in-Time Recovery — voltar a um segundo exato).

2. Backup Lógico vs. Backup Físico (e PITR)

Os SGBDs oferecem duas abordagens complementares para extrair cópias de segurança sem interromper os usuários (Hot Backup):

  • Backup Lógico (Dump SQL): Exporta as instruções CREATE TABLE e INSERT em texto ou formato compactado. É excelente para portabilidade entre versões ou migração de tabelas específicas, mas é lento para restaurar bancos de centenas de gigabytes.
  • Backup Físico (Binário / Snapshot): Copia diretamente os arquivos de blocos de dados em disco e os logs de transação (WAL / Redo Log). É extremamente rápido tanto para copiar quanto para restaurar grandes volumes, exigindo a mesma arquitetura/versão do SGBD.
# === Exemplos de Linha de Comando (PostgreSQL e MySQL) ===

# 1. PostgreSQL - Backup Lógico compactado (pg_dump)
pg_dump -U postgres -F c -b -v -f "backup_loja_2026.dump" db_loja

# 2. PostgreSQL - Restauração Lógica (pg_restore)
pg_restore -U postgres -d db_loja_restaurado -v "backup_loja_2026.dump"

# 3. PostgreSQL - Backup Físico base para PITR (pg_basebackup)
pg_basebackup -U replicador -D /var/backups/pg_fisico -Ft -z -Xs -P

# 4. MySQL - Backup Lógico consistente sem travar tabelas InnoDB
mysqldump -u root -p --single-transaction --routines --triggers db_loja > backup_loja.sql
Recuperação Pontual (PITR — Point-in-Time Recovery): Se um analista rodar por engano um DELETE FROM clientes; sem WHERE às 14:32:10, o DBA restaura o último backup físico e aplica os arquivos de log de transações (WAL/Binlog) parando exatamente às 14:32:09 — recuperando todos os dados até 1 segundo antes do acidente!

3. A Regra 3-2-1 e Testes de Restauração

Para proteger o banco contra falhas de hardware, incêndios e ataques de ransomware, adota-se o padrão internacional 3-2-1:

  1. 3 cópias dos dados (1 base original em produção + 2 cópias de backup).
  2. 2 mídias ou armazenamentos distintos (ex.: disco local/NAS + armazenamento de objetos em nuvem como AWS S3 / GCS).
  3. 1 cópia fora do local físico (off-site) e preferencialmente imutável (protegida contra exclusão ou criptografia maliciosa).
Regra de Ouro do DBA: "Um backup que nunca foi testado não é um backup, é apenas uma esperança." Agende simulações periódicas de restauração em um servidor isolado para validar a integridade dos arquivos e medir se o tempo real de recuperação atende ao RTO prometido.

4. Exercícios de Fixação

Avalie seus conhecimentos sobre estratégias de backup e recuperação de dados:

1. Uma empresa realiza backup Full no domingo e backups Incrementais de segunda a sexta. Se o servidor falhar na quinta-feira à noite, quais arquivos de backup são obrigatórios para restaurar o banco até quinta-feira?

Ver resposta comentada
São obrigatórios cinco arquivos em sequência: o backup Full de domingo + os backups Incrementais de segunda, terça, quarta e quinta-feira. Se qualquer um dos incrementais intermediários estiver corrompido, a cadeia é quebrada a partir daquele dia. (Se fosse backup Diferencial, bastariam o Full de domingo + o Diferencial de quinta).

2. Qual recurso de recuperação permite restaurar um banco de dados exatamente ao estado em que estava minutos antes de um comando UPDATE sem WHERE ser executado acidentalmente?

Ver resposta comentada
O PITR (Point-in-Time Recovery — Recuperação Pontual), que combina a restauração de um backup físico base com a reaplicação controlada dos arquivos de log de transações (WAL no PostgreSQL, Binlog no MySQL ou Transaction Log no SQL Server) até o instante exato anterior ao erro.

3. Qual a diferença entre os indicadores RPO e RTO no planejamento de desastres?

Ver resposta comentada
O RPO (Recovery Point Objective) mede a perda máxima aceitável de dados medida em tempo (ex.: perder no máximo 5 minutos de transações), enquanto o RTO (Recovery Time Objective) mede o tempo máximo aceitável de indisponibilidade para colocar o sistema no ar novamente.

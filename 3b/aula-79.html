Aula 79: Segurança em Bancos Relacionais

Aprenda a proteger ambientes de banco de dados aplicando o princípio do privilégio mínimo por meio de Gestão de Usuários, Controle de Acesso Baseado em Papéis (RBAC), comandos DCL (GRANT / REVOKE), criptografia (em repouso e em trânsito) e prevenção contra SQL Injection.

1. Controle de Acesso e Comandos DCL (GRANT e REVOKE)

A segurança de um SGBD baseia-se no Princípio do Privilégio Mínimo: cada usuário, aplicação ou serviço deve possuir apenas os privilégios estritamente necessários para realizar suas funções, jamais operando com credenciais de administrador (como postgres ou root).

O subconjunto DCL (Data Control Language) gerencia essas permissões por meio dos comandos GRANT (conceder) e REVOKE (retirar):

-- 1. Criar um usuário/login com senha segura
CREATE USER app_financeiro WITH PASSWORD 'SenhaForte#2026_Sec';

-- 2. Conceder permissões granulares de DML apenas na tabela necessária
GRANT SELECT, INSERT, UPDATE ON transacoes TO app_financeiro;

-- 3. Revogar privilégios acidentais ou excessivos
REVOKE DELETE ON transacoes FROM app_financeiro;
Gerenciamento por Papéis (RBAC — Role-Based Access Control): Em vez de conceder privilégios diretamente a dezenas de usuários individuais, crie papéis/perfis (ex.: CREATE ROLE analistas;), atribua permissões a esse papel e adicione os usuários ao papel (GRANT analistas TO joao, maria;).

2. Proteção de Dados: Criptografia e Mascaramento

Para cumprir regulamentações de privacidade (como a LGPD e o GDPR), os dados sensíveis exigem proteção em múltiplas camadas:

  • Criptografia em Trânsito (TLS/SSL): Garante que todas as consultas e dados trafegados entre a aplicação cliente e o servidor SGBD estejam criptografados, impedindo ataques de escuta na rede (sniffing).
  • Criptografia em Repouso (TDE — Transparent Data Encryption): Criptografa os arquivos de dados, índices e logs diretamente no disco rígido do servidor, protegendo o banco contra furto físico de storages ou backups.
  • Mascaramento de Dados (Dynamic Data Masking): Oculta parte de informações sensíveis (como exibir apenas os últimos 4 dígitos do CPF ou cartão de crédito: ***.***.***-89) para usuários comuns, enquanto administradores ou sistemas autorizados visualizam o dado completo.

3. O Vetor de Ataque Número 1: SQL Injection

O SQL Injection ocorre quando uma aplicação concatena entradas de usuário diretamente em strings de comandos SQL, permitindo que invasores alterem a lógica da consulta para burlar autenticação ou extrair/apagar tabelas inteiras.

Abordagem Exemplo de Código Vulnerável ou Seguro Nível de Segurança
Inseguro (Concatenação) "SELECT * FROM usuarios WHERE email = '" + userInput + "';" CRITICAMENTE VULNERÁVEL a SQL Injection.
Seguro (Prepared Statements) SELECT * FROM usuarios WHERE email = $1; (com parâmetros separados) SEGURO (o SGBD trata a entrada estritamente como dado, nunca como código SQL).
Regra Absoluta de Desenvolvimento: Nunca confie em dados vindos do cliente (formulários web, APIs, parâmetros de URL). Utilize sempre Prepared Statements (Consultas Preparadas), ORMs seguros ou procedimentos armazenados parametrizados em todas as camadas da aplicação.

4. Exercícios de Fixação

Teste seus conhecimentos sobre segurança e privilégios em bancos de dados relacionais:

1. O que significa o Princípio do Privilégio Mínimo (Least Privilege) na administração de um SGBD?

Ver resposta comentada
Significa conceder a cada usuário, sistema ou aplicação apenas as permissões mínimas indispensáveis para a execução de suas tarefas específicas, proibindo o uso desnecessário de contas superusuárias (como root ou postgres) em rotinas cotidianas.

2. Por que a concatenação direta de variáveis de usuário em strings SQL (ex.: "SELECT * FROM users WHERE user = '" + nome + "'") expõe o banco de dados a ataques de SQL Injection?

Ver resposta comentada
Porque se a variável nome contiver caracteres especiais de comando SQL (como aspas simples ' OR '1'='1), o interpretador do SGBD passará a executar o texto inserido pelo usuário como se fosse parte da estrutura do comando original, alterando a lógica da consulta.

3. Qual a principal vantagem de utilizar papéis (ROLE) em vez de atribuir permissões individualmente a cada um dos 50 funcionários do setor financeiro?

Ver resposta comentada
A centralização e escalabilidade da gestão de acessos. Se a empresa precisar alterar uma permissão ou adicionar uma nova tabela para o setor financeiro, basta atualizar o ROLE financeiro uma única vez, refletindo automaticamente em todos os usuários associados a esse papel, em vez de alterar 50 contas separadamente.

Semana 26 — Aula 2

Backup e Recuperação no MongoDB

Estratégias de Backup em Bancos NoSQL

Garantir a integridade dos dados em caso de falhas de hardware, corrupção de sistema ou erro humano exige uma estratégia robusta de backup. No MongoDB, existem duas abordagens principais: Backups Lógicos (exportação de dados em BSON/JSON) e Backups Físicos / File-System Snapshots.

1. Backups Lógicos com `mongodump` e `mongorestore`

As utilidades de linha de comando mongodump e mongorestore lêem e escrevem diretamente os documentos BSON do MongoDB. São ideais para bases pequenas a médias ou para exportação de coleções específicas.

Exportando um Banco de Dados (`mongodump`):

# Backup simples da base 'escola_db' comprimido em formato gzip
mongodump --uri="mongodb://adminEscola:senha@localhost:27017" \
          --db=escola_db \
          --gzip \
          --out=/backups/2026-03-01/

Restaurando o Banco de Dados (`mongorestore`):

# Restaurando a base 'escola_db' a partir do backup comprimido
mongorestore --uri="mongodb://adminEscola:senha@localhost:27017" \
             --db=escola_db \
             --gzip \
             /backups/2026-03-01/escola_db/

Dica de Consistência (Oplog): Ao executar o mongodump em um Replica Set em produção, adicione a flag --oplog. Isso captura todas as modificações ocorridas durante a execução do backup, garantindo uma cópia consistente do ponto no tempo.

2. Backups Físicos e Snapshots de Sistema de Arquivos

Para bases com terabytes de dados, o backup lógico pode ser muito lento. A solução recomendada é realizar File-System Snapshots (como LVM no Linux, AWS EBS Snapshots ou Azure Managed Disks).

  • Em Replica Sets: Pausa-se a sincronização em um nó *Secondary* (db.fsyncLock()), tira-se o snapshot dos arquivos do diretório de dados (`/var/lib/mongodb`) e desbloqueia-se o nó (db.fsyncUnlock()).
  • Vantagem: Cópia instantânea em nível de bloco com tempo de recuperação (RTO) extremamente reduzido.

3. Point-in-Time Recovery (PITR)

O Point-in-Time Recovery permite restaurar a base de dados exatamente no estado em que ela se encontrava num segundo específico antes de um evento catastrófico (ex: a execução acidental de um dropDatabase() às 14:32h).

Essa técnica combina a restauração do último backup físico/lógico completo com a aplicação sequencial do log de operações (oplog) até a marca de tempo exata desejada.

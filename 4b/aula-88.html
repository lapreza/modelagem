Modelagem de Dados em Bancos NoSQL

A Filosofia da Modelagem NoSQL

No mundo relacional (SQL), a modelagem é focada nas **entidades e nas regras de normalização** para evitar duplicidade a todo custo. No NoSQL, a modelagem é orientada a **padrões de acesso e consultas da aplicação (Query-Driven Design)**.

Regra de Ouro em NoSQL: Modele os seus dados de acordo com a forma como a sua aplicação lê e escreve as informações, mesmo que isso signifique duplicar dados propositadamente (Desnormalização).

Estratégia 1: Dados Embutidos (Embedding / Denormalization)

Os dados relacionados são armazenados diretamente dentro de um único documento ou estrutura como subdocumentos ou arrays.

Exemplo de Documento Embutido (JSON):

{
  "_id": "usr_101",
  "nome": "Rafael Lapreza",
  "email": "rafael@email.com",
  "enderecos": [
    { "tipo": "Residencial", "cidade": "Sumaré", "uf": "SP" },
    { "tipo": "Comercial", "cidade": "Americana", "uf": "SP" }
  ]
}

Quando Usar Embutimento?

  • Relacionamentos de **1:1** ou **1:N** onde N é pequeno e limitado (ex.: endereços de um cliente, itens de um pedido).
  • Dados que são quase sempre lidos e atualizados juntos na aplicação.

Estratégia 2: Referenciamento (Referencing / Normalized)

Os dados são mantidos em documentos ou coleções separadas e ligados através de identificadores (IDs), funcionando de forma similar às chaves estrangeiras relacionais.

Exemplo de Referenciamento:

// Documento da Coleção 'autores'
{ "_id": "aut_50", "nome": "Andrew S. Tanenbaum" }

// Documento da Coleção 'livros'
{
  "_id": "liv_900",
  "titulo": "Sistemas Operacionais Modernos",
  "autor_id": "aut_50"
}

Quando Usar Referenciamento?

  • Relacionamentos **1:N** onde N é ilimitado/muito grande (ex.: logs de acesso de um usuário, seguidores em uma rede social).
  • Relacionamentos **N:M** (Muitos para Muitos).
  • Quando o dado referenciado muda com muita frequência e é compartilhado por múltiplos documentos.
